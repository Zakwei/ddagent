ddagent поставляет **локальную базу знаний** для ваших агентов: воспоминания, правила,
навыки и личную информацию, а также теги и связи. Она живёт в той же
базе SQLite, что и остальной ddagent (`auth.db`), за полнотекстовым индексом
FTS5, управляется с экрана **Knowledge** в клиенте и доступна
для чтения и записи вашим агентам через MCP. Она вольно вдохновлена
[Contexta](https://github.com/XFABISIEK/Contexta).

Суть проста: ваши правила и знания о проекте перестают быть разбросанными
по файлам отдельных инструментов (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `skills/`, …)
и становятся одним выверенным, доступным для поиска местом, которым может пользоваться
каждый агент — и те, что читают файлы, и те, что говорят на MCP.

## Как агент на самом деле это видит

Есть три слоя, и полезно понимать, какой из них какой:

- **Нативные файлы CLI** — каждый инструмент читает свою конфигурацию сам: Claude Code
  читает `CLAUDE.md`, Codex/Cursor читают `AGENTS.md`, Cursor читает `.cursorrules`,
  а некоторые читают `skills/` и `.agents/skills/`. Это работа CLI, а не
  выбор модели — ddagent это не отключает.
- **Инъекция ddagent** — на первом ходу сессии ddagent добавляет в начало
  блок `<knowledge>` (подробности ниже). Это работает для любого провайдера и не требует
  никакой настройки со стороны агента.
- **Инструменты MCP** — как только вы установите MCP-сервер ddagent в агента, его список
  инструментов будет включать `knowledge_search` и компанию. Модель решает, когда их
  вызывать, руководствуясь описаниями инструментов и любыми инструкционными правилами, которые вы храните в
  базе знаний.

Так что «одно место» означает **одно место для курирования внедряемого контента и один бюджет**
— оно не мешает (и не может помешать) CLI читать свои собственные нативные файлы. Чтобы избежать
дубликатов, мы держим рабочее `AGENTS.md` на приоритете `high`, чтобы блок знаний
никогда не повторял то, что уже внедряют unified-rules.

## Сущности

| Сущность | Область | Примечания |
|---|---|---|
| Воспоминание | проект или глобально | `memory_type` (`fact`/`decision`/`note`/`reference`), `priority`, `source`, теги |
| Правило | проект или глобально | переключатель `enabled`; правила `critical` внедряются в сессии |
| Навык | глобально | уникальное имя, категория, необязательная иконка (base64 data URL) |
| Личная информация | глобально | уникальный `key` |
| Тег / Связь | — | теги на воспоминаниях; связи соединяют любые две сущности |
| История | — | каждая запись делает снимок сущности, чтобы её можно было просмотреть и восстановить |

Приоритеты: `critical > high > normal > low`. Сущность можно ограничить одним
проектом или сделать глобальной (применяется везде). `project_id` — обычный столбец (без
внешнего ключа), потому что таблица проектов перестраивается во время миграций.

## Инъекция на первом ходу (что каждый агент получает автоматически)

На **первом** исходящем сообщении сессии ddagent добавляет в начало блок
`<knowledge>`, содержащий:

- **правила** `critical` (проектные + глобальные, только включённые),
- **воспоминания** `critical`,
- каждую запись **личной информации**,
- **соседей на 1 шаг** включённых воспоминаний (достигаемых через явные
  связи).

Весь блок ограничен ~4000 токенов. Он проходит через тот же шлюз первого хода, что
`.ddagent/shared-context.md` и unified rules, поэтому не расходует токены на каждый ход.
Установите `DDAGENT_KNOWLEDGE=0`, чтобы отказаться.

Панель показывает **измеритель внедрённого контекста** (`~X / 4000 tok`) для
выбранного проекта, так что вы видите и контролируете, что попадает в контекст.

## Инструменты MCP (по запросу)

MCP-сервер ddagent (`POST /mcp`) открывает базу знаний любому MCP-клиенту.
Инструменты чтения работают с токеном области `read`; инструменты записи требуют `write`.
Инструменты записи выполняют ту же валидацию, что и UI, и сохраняют историю.

Чтение: `knowledge_search`, `knowledge_get_context`, `knowledge_get_memories`,
`knowledge_get_rules`, `knowledge_get_skills`, `knowledge_get_personal`,
`knowledge_get_graph`, `knowledge_history`.

Запись: `knowledge_add_memory`, `knowledge_update_memory`,
`knowledge_delete_memory`, и та же тройка для `rule`, `skill` и `personal`;
плюс `knowledge_link` / `knowledge_unlink`.

Инструменты принимают либо `projectId`, либо `projectPath`, который ddagent уже знает.

### Установка сервера в ваших агентах

Вам не нужно редактировать конфигурации провайдеров вручную. Используйте **Settings → MCP →
Install ddagent MCP server** (также предлагается как шаг онбординга) и выберите
агентов — или установите для всех. Он записывает HTTP MCP-запись `ddagent` (область
пользователя), указывающую на `<server>/mcp`, с переиспользуемым bearer-токеном
`ddagent-mcp` (переустановка отзывает предыдущий). После установки инструменты этого
агента включают группу `knowledge_*` рядом с `create_task`, `send_message` и т. д.

Откуда агент знает, *когда* использовать MCP? Он не угадывает — скажите ему. Держите
правило `critical`, например: *«Прежде чем отвечать на вопросы об этом проекте, вызови
`knowledge_search`; когда принимаешь решение, зафиксируй его через
`knowledge_add_memory`».* Поскольку это правило внедряется на каждом первом ходу, все
ваши агенты получают одни и те же рабочие инструкции.

## Сканирование проекта

`POST /api/knowledge/scan` импортирует AI-контекстные файлы проекта, классифицируя по
назначению:

- `AGENTS.md`, `CLAUDE.md`, `MUSE.md`, `GEMINI.md`, `CODEX.md`, `.cursorrules`,
  `.muserules` и markdown/`.mdc` под `.cursor/rules` становятся **правилами**
  (critical + enabled, поэтому они доходят до контекста агента; рабочее `AGENTS.md`
  — `high`, чтобы избежать двойной инъекции с unified-rules),
- файлы `SKILL.md` под `skills` / `.agents/skills` становятся **навыками**
  (имя/описание из frontmatter),
- любой другой просканированный markdown становится **справочным воспоминанием**.

Каждый файл отслеживается по хешу содержимого в `kb_scan_state`, поэтому повторное сканирование
касается только изменённых файлов и удаляет сущности, чей источник исчез.

## Клиент

Экран **Knowledge** (рейл навигации → Knowledge) имеет вкладки Dashboard, Memories,
Rules, Skills, Personal и Graph, фильтр области проекта, модальную форму
создания/редактирования, историю версий по сущностям с восстановлением, загрузку иконок
навыков и экспорт/импорт JSON. На вкладке Memories есть панель фильтра тегов (с
управлением тегами), в панели приложения — полнотекстовый поиск, диалог создания связи и
действие миграции, а вкладка Graph — это силовой граф связей с панорамированием/зумом,
перетаскиванием узлов, фильтрами по типу сущности и подсветкой соседей.

## Как хорошо это курировать

1. **Просканируйте** каждый активный проект один раз (Knowledge → выберите проект → scan);
   повторяйте сканирование после больших изменений в его инструкционных файлах.
2. **Повышайте осознанно**: только действительно обязывающие правила должны быть `critical`
   (они внедряются). Используйте звезду в строке и следите за измерителем бюджета.
3. **Остальное держите как `high`/`normal`** — всё ещё доступно для поиска и через MCP
   без расхода контекста на каждом ходу.
4. **Личная информация** для предпочтений между проектами (часовой пояс, редактор, именование).
5. **Связывайте родственные воспоминания**, чтобы соседи на 1 шаг ехали вместе.
6. **Установите MCP** для агентов, которым следует искать в базе и фиксировать
   знания; дайте область `read` большинству, `write` — там, где доверяете агенту.

## Миграция

Knowledge → меню → **Migrate existing rules** запускает отчёт **dry-run**: он
сканирует все проекты, находит дубликаты, существующие между проектами (одинаковый
нормализованный заголовок + содержимое), и показывает количество правил. Оттуда можно **Merge duplicates**
(схлопывает их в одну глобальную строку) и/или **Make all rules critical**. Ничего
не записывается, пока вы не подтвердите — деструктивные действия явны.

**Dashboard** также содержит одну кнопку **Импортировать всё в ddagent**: она выполняет сканирование проекта и импорт навыков агентов одним действием, с тем же предпросмотром dry-run и необязательными переключателями объединения дубликатов / повышения. Она только читает файлы ваших агентов и записывает в собственную базу данных ddagent — ни файл, ни конфигурация CLI не затрагиваются (единственное действие, которое записывает в конфигурацию агента, — это отдельный "Install ddagent MCP server").

В том же меню есть **Импорт навыков агентов**: он перечисляет глобальные/стандартные навыки, которые ваши агенты уже поставляют или установили (области пользователя / системы / плагина), и импортирует недостающие в базу знаний как навыки. Сначала это dry-run, и он идемпотентен — имя, которое уже существует, пропускается. Навыки с областью проекта импортируются вместо этого сканированием проекта.

## Полезно знать

- Всё **локально** для этого экземпляра ddagent; без облака и синхронизации.
- Инъекция происходит **раз за сессию** (первый ход) — новые сессии подхватывают
  изменения.
- Просканированные навыки **не внедряются**; они достижимы через поиск MCP,
  что сохраняет постоянный контекст компактным.
- Правило или воспоминание может быть изменено агентом через MCP; просмотрите изменения в
  **Истории** сущности и при необходимости восстановите предыдущую версию.

## REST API

Смонтирован на `/api/knowledge` за аутентификацией:

```
GET    /memories            ?projectId=&includeGlobal=&priority=&tag=&memoryType=&limit=&offset=
POST   /memories            PATCH /memories/:id   DELETE /memories/:id
GET    /rules               ?projectId=&includeGlobal=&priority=&enabledOnly=
POST   /rules               PATCH /rules/:id       DELETE /rules/:id
GET    /skills              ?category=
POST   /skills              PATCH /skills/:id      DELETE /skills/:id
GET    /personal            POST /personal         PATCH/DELETE /personal/:id
GET    /search              ?q=&type=&projectId=&limit=
GET    /graph               ?projectId=&types=&limit=
GET    /context             ?projectId=            (injection preview + budget)
GET    /tags                DELETE /tags/:id
GET    /connections         POST /connections      DELETE /connections/:id
GET    /history             ?entityType=&entityId=&limit=
GET    /stats
GET    /export              POST /import
POST   /scan                { projectId }
POST   /migrate             { projectIds?, dryRun?, dedupe?, promoteRules? }
POST   /import-skills       { providers?, scopes?, dryRun? }
POST   /import-all          { dryRun?, dedupe?, promoteRules? }
```

`projectId=global` ограничивает список глобальными строками; добавление `includeGlobal=true`
к id проекта возвращает строки проекта плюс глобальные.
